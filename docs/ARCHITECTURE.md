prediction was pessimistic by roughly 3x, and the proposed mitigation is *slower* than the
standard library at every size tested, including the variant that avoids position tracking
entirely. Rust's `BinaryHeap` uses a hole-based sift that beats a straightforward swap loop,
and higher arity made things worse rather than better here. Use `std::collections::BinaryHeap`
and spend the effort on keeping it small.

## 3. Analytic epoch advancement

This is the core mechanism, so it is worth stating precisely.

### 3.1 The decode recurrence has a closed form

Within an epoch the batch composition is fixed: `B` sequences are decoding, none finishes,
none is admitted. From the primer's cost model, per-GPU bytes read at step `k` are the
weights plus the resident KV, and the resident KV grows by exactly `B` tokens per step.

Let `G` be tensor-parallel degree, `bw` HBM bandwidth, `u` memory-bandwidth utilization,
`kv` bytes of KV per token, `W` total weight bytes, `S0` resident KV tokens at epoch start,
and `t_fix` fixed per-step overhead. Then

```
alpha = kv * B / (G * bw * u)                     # step-time growth per step
beta  = (W + kv * S0) / (G * bw * u) + t_fix      # duration of the first step
t_step(k) = beta + alpha * k
```
Issao: Is this modeling just the HBM bandiwdth cost and not the GPU cost? I would expect
it to be the worst of the two.

Summing an arithmetic series gives the duration of `n` steps in closed form:

```
T(n) = n * beta + alpha * n * (n - 1) / 2
```

### 3.2 Advancing an epoch is O(1)

The next composition change is at `n* = min(tokens_remaining_i)` over the batch, available
in O(1) from a small min-structure per replica. The epoch therefore ends at `t + T(n*)`,
computed with a handful of arithmetic operations regardless of whether `n*` is 3 or 30,000.

If an external event lands mid-epoch at offset `d` (an arrival, a preemption order, a
policy decision), invert the quadratic to find how many steps have elapsed:

```
n = floor( ( -(beta - alpha/2) + sqrt( (beta - alpha/2)^2 + 2*alpha*d ) ) / alpha )
```

Advance the epoch state to step `n`, apply the event, and open a new epoch. Also O(1).

### 3.3 What this buys, and what it costs

- Cost becomes O(composition changes), independent of token counts. This is exactly the
  principle you stated in VISION section 4: work scales with number of requests, not with
  the size of the work in each request.
- It is **exact**, not approximate, given the linear-bandwidth cost model. The
  approximation lives in the cost model, which is calibrated, not in the integration.
- Per-sequence identity, arrival order, and completion times are all preserved, so tail
  latency and per-tenant fairness remain measurable.

### 3.5 Validated numerically

`bench/validate_epochs.py` checks the claim rather than asserting it. Three properties, all
passing:

- **The closed form equals the step-by-step sum exactly**, checked in rational arithmetic
  rather than floating point, across batch sizes from 1 to 256 and up to 30,000 steps. A match
  in exact arithmetic is a proof for those inputs, not a coincidence of rounding.
- **The inverse solve is correct** on 20,000 randomised trials plus exact-boundary cases: for a
  mid-epoch event at offset `d`, the returned step count `n` satisfies `T(n) <= d < T(n+1)`.
- **A whole replica run agrees.** Sequences with different remaining lengths, completing at
  different times, produce identical completion times either way. Worst relative difference
  across cases was 1.7e-15, which is float noise and not algebraic disagreement. The same runs
  took 23,343 per-step iterations versus 285 epoch iterations, a factor of 82.

A side finding worth keeping: the closed form is *more* accurate than the loop, not merely
faster, because it does not accumulate rounding error over n additions. That removes the last
reason someone might prefer per-step iteration.

The same script reproduces the decode step-time table in `docs/llm-serving-primer.md` section
10.4 to within 0.1 ms at every row, which is a useful check that the algebra here and the
hand-computed numbers there describe the same model.

## 4. Pressure test: request cohorts

Your open question, answered directly. **Recommendation: do not build cohorts.**

**The problem they solve is not the problem you have.** Cohorts reduce per-request cost.
Per-request cost at target scale is ~165 MB of state and ~112,500 arrivals/s, which is
cheap. The expensive thing was per-token work, and epochs remove that completely without
any loss of fidelity.

**They destroy the dynamics you named as goals.** Every phenomenon in VISION section 3a is
driven by *heterogeneity between individual requests*:

- Rolling hotspots exist because request sizes differ. A cohort with a mean size has no
  hotspot to roll.
- Head-of-line blocking is one long request stalling many short ones. Averaged into a
  cohort, the stall disappears.
- Preemption cascades start when a few sequences outrun their expected output length.
  Cohort means cannot express "a few".
- Goodput, p99, and p99.9 are order statistics over individual requests. They cannot be
  recovered from cohort aggregates. Your entire scorecard is per-request.

**The cohort=1 to cohort=infinity dial is not monotone in usefulness.** It is monotone in
cost, but fidelity collapses non-linearly: the first bit of aggregation removes the
heterogeneity, which is where nearly all the interesting behaviour lives. A dial whose
first click destroys the phenomenon is not a useful dial.

**Where an aggregate model genuinely earns its place.** Three narrow uses, all opt-in and
explicitly labelled approximate:

1. **Background regions.** In a five-cluster geo scenario where you are studying cluster 2,
   simulate clusters 1, 3, 4, 5 as fluid load so they still create realistic cross-region
   routing pressure and shared-capacity contention, at ~1% of the cost.
2. **Warm-up.** Reach a realistic steady state quickly before switching to request-level.
3. **Long-horizon fast-forward.** Days of diurnal traffic to study autoscaling drift, where
   only the aggregate envelope matters, with request-level enabled in windows of interest.

That is a `fidelity = full | fluid` flag *per cluster and per time window*, not a global
aggregation parameter. It preserves full fidelity where you are looking.

## 5. Engine, policy, and the physics referee

Your section 10 concern, resolved.

### 5.1 Policies produce intents, never mutations

A policy is a pure function from a **stale observation** to a list of **intents**. It holds
its own private state (estimators, EWMAs, controller integrators) but never touches
simulation state.

```
trait Policy {
    fn decide(&mut self, obs: &Observation, out: &mut IntentBuffer);
}
```

Intents are a closed enum: `Route`, `Admit`, `Reject`, `Enqueue`, `Preempt`, `Resume`,
`SetStepBudget`, `SetBatchLimit`, `MigrateKv`, `ScalePool`, `EjectReplica`, `Retry`.

### 5.2 The referee enforces physics

Every intent passes through a referee that checks the invariants a policy must not be able
to violate:

- **Conservation.** Tokens are neither created nor destroyed; a request's output length is
  fixed by the workload model, not choosable by the scheduler.
- **Capacity.** Resident KV tokens never exceed a replica's budget. Step token budget never
  exceeds the engine maximum. Batch size never exceeds `max_num_seqs`.
- **Causality.** No intent may reference state newer than the observation it was derived
  from, and no scheduled effect may land earlier than the applicable actuation delay.
- **Bandwidth.** Every KV migration debits the shared fabric or tier bandwidth for its
  duration.
- **Work completion.** Admitted work is either completed, preempted, or explicitly failed.
  It cannot silently vanish.

Two modes: `strict` aborts on violation, used in tests and in the policy arena so a cheating
policy cannot score; `tolerant` clamps and records a counter, so an agent-written policy
degrades instead of crashing a long run.

This is what makes the agent arena in your section 10 trustworthy. Cheating is not
punished after the fact, it is unrepresentable: the observation type has no fresh state in
it, and the intent type cannot express a physics violation that the referee will pass.

### 5.3 The performance worry does not materialize

You suspected the policy would need to compute machine state itself for speed. With
analytic epochs the engine's cost per decision is a handful of arithmetic operations, so
there is nothing to gain by moving that into the policy. Keep the separation clean.

## 6. Staleness, delay, and the control-theory angle

This deserves first-class treatment because it is your most distinctive goal, and it is
cheap to build.

### 6.1 Every observation is delayed by construction

```
replica true state
  -> sampling (period T_s, jitter)          # sensor
  -> publish (propagation delay, loss)      # transport
  -> consumer's last-known value            # zero-order hold
  -> Observation handed to policy           # the only thing a policy can see
```

The `Observation` type contains a timestamp and no channel to fresh state. A policy that
wants fresher information must pay for it in the model, for example by probing, which costs
a modelled RPC. That makes the cost of freshness visible rather than free.

### 6.2 The loop is a textbook sampled-data control system

- Plant: replica queues and KV occupancy.
- Sensor: telemetry with period `T_s` and delay `tau`.
- Controller: the load-balancing or autoscaling policy.
- Actuator: routing takes effect after an RPC delay; autoscaling after cold start, which is
  30-300 s from the primer. That is an enormous actuator delay and the reason reactive
  autoscaling oscillates.

Two features worth building because they turn this from an anecdote into analysis:

1. **Perturbation input.** Drive offered load with a step, or a sinusoid at frequency `f`,
   independent of the baseline workload.
2. **Frequency sweep.** Run the sinusoid across a range of `f` and record gain and phase
   from offered load to observed queue depth. That produces an empirical Bode plot, from
   which you get loop gain and phase margin, and you can *predict* the onset of oscillation
   rather than just observe it. Comparing a naive proportional controller against one with
   damping or a delay-compensating estimator then becomes quantitative.

I have not seen this done for inference serving. It is a genuinely novel and cheap addition,
and it makes the "value of robust control logic" claim measurable.

### 6.3 Gray failure

Replica health is a vector, not a boolean:

| Field | Meaning |
|---|---|
| `announced_state` | what the replica reports: healthy, draining, down |
| `speed_multiplier` | true throughput scaling; 0.1 is a thermal or degraded-link straggler |
| `accept_but_stall` | accepts requests and never completes them: partition or deadlock |
| `telemetry_state` | stale, frozen, or lying |

Silent slowdown is `announced_state = healthy` with `speed_multiplier = 0.1`. Detection
latency then becomes a measurable policy property rather than an assumption.

## 7. Data locality

### 7.1 KV capacity is the primary constraint

Per replica, KV capacity in tokens is
`(HBM_per_GPU * G - weight_bytes - workspace) / kv_bytes_per_token`, about 1.37 M tokens
for the reference config. Model it as a token counter with block-granularity rounding.
PagedAttention makes fragmentation a second-order effect, so it is out of scope.

The live KV and the prefix cache **compete for the same budget**. That coupling is a real
dynamic: under load the prefix cache is squeezed, hit rate falls, prefill work rises, and
load rises further. Model the split as a policy knob, because it is one in reality.

### 7.3 Prefix caching: feasible, recommended

You suspected this approaches a cluster-wide virtual memory table. It does not, because of
one observation: **you never need to model content, only how much of a request's prompt is
already resident on a given replica.**

Represent shared prefixes as a **tree of segments**:

```
PrefixNode { parent: NodeId, tokens: u32, id: NodeId }
```

- A request carries one `NodeId` plus its own unshared suffix length.
- Sharing is *generated by the workload model*, not discovered from content. Turn N of a
  session extends turn N-1's node. A shared system prompt is a common root. A multi-agent
  fork or a tree search creates siblings under a shared parent. This is exactly the
  structure real traffic has, and it is free to construct.
- Per replica, a hash map from `NodeId` to residency, with an LRU over nodes.
- Hit length on replica R = walk from the request's node up through ancestors, summing the
  tokens of resident ones. Depth is a handful, so the lookup is O(depth), independent of
  prompt length.

Cost: O(1) to O(depth) per request. Memory: one entry per cached node per replica, which
must be capped, see section 1.5. Eviction competes with live KV, which is the coupling that
makes it interesting.

This directly supports the affinity questions in your section 3b, including the failover
cascade in 3a: when an affinity hotspot fails over, the new replica has a cold cache, its
prefill load spikes, and it becomes slow, which is the cascade. That dynamic is only
reachable if prefix state is modelled. **Recommend building it, in phase 2.**

## 8. Determinism, replay, and observability

### 8.1 Determinism

One global seed. Named independent streams derived from it, so that changing the arrival
rate does not perturb prompt lengths, and enabling failure injection does not perturb the
workload. Without stream independence an A/B comparison silently compares two different
workloads. Stream names are hashed with a stable hash, never a per-process-salted one.

The engine's tie-breaking must be total and payload-independent: order by
`(time, priority, sequence_number)` where sequence number is a monotonic insertion counter.
No iteration over a hash map may ever influence scheduling order. A run should emit a
fingerprint, for example event count plus a rolling checksum of applied intents, so
determinism is a test rather than a hope.

### 8.2 Replay and the fast-forward/rewind UI

Two candidate mechanisms, and the cheap one is better:

- **Snapshot and re-simulate.** State is ~1.3 GB, so snapshots are expensive to take often.
  Use a coarse interval, for example every 60 simulated seconds, for long runs.
- **Observable event log, recommended for the UI.** Record what the dashboard can display:
  time series, histograms per interval, and sampled request traces. Scrubbing, fast-forward,
  and rewind then read the log with no re-simulation at all. Only a parameter change
  requires re-running.

So: log-driven scrubbing for the interactive dashboard, coarse snapshots only to bound
re-simulation cost when a user changes a parameter mid-run.

### 8.3 Metrics must aggregate online

An hour at target scale is ~405 M request completions. Design accordingly:

| Data | Mechanism | Volume |
|---|---|---|
| Latency distributions | HDR-style histograms per (cluster, tenant, SLO class, interval) | bounded |
| Time series | fixed-rate gauges, time-weighted | bounded |
| Counters | monotonic totals | trivial |
| Full request traces | reservoir sampling, uniform **plus** per-latency-bucket | bounded, tunable |

Your requirement for latency-bucket-stratified trace sampling is essential rather than
optional: uniform sampling of 405 M requests will contain almost no p99.9 examples, and
those are the ones worth reading. Stratify by outcome and latency bucket so the interesting
tail is always represented.

## 9. Parallelism and deployment

Parallel discrete-event simulation is genuinely hard, so avoid needing it.

**Within one simulation.** Section 1.3 shows one core per cluster clears 20x realtime. So
run one thread per cluster, synchronised conservatively using the minimum inter-cluster
latency as lookahead. Cross-region latency is 10-100 ms, so a cluster can safely advance
10 ms of simulated time without hearing from its peers, which is 100 barriers per simulated
second. That is cheap and, importantly, still deterministic.

Do **not** attempt to parallelise within a cluster in v1. Intra-cluster RPC latency is
0.2-1 ms, so the safe lookahead is small, barriers become frequent, and the complexity is
not justified by a workload that already fits in one core.

**Across simulations.** This is the parallelism you actually want. The primary use is A/B
comparison, so running 20 scenario variants concurrently is embarrassingly parallel, needs
no time synchronisation, and is trivially deterministic.

**Deployment.** Ten GCP backend replicas are for serving many concurrent users and scenario
runs, not for splitting one simulation. Sharding a single run across processes should be a
last resort. Worth stating plainly in the design so nobody builds a distributed time-warp
engine that is not needed.

## 10. The system in words

`docs/diagrams/system.drawio` draws this, in two pages: the data plane with its policy
boundary, and the control plane with the engine and product surface. Every arrow there names
a `service.Method` in `proto/`, and `tools/check_diagram.py` fails if the diagram and the
interfaces disagree. What follows is the same thing in prose, which is the authoritative
version.

### 10.1 The life of a request

A **workload generator** stands in for clients. It draws an arrival time, a tenant, an SLO
class, a prompt length, and a shared-prefix identity. It also draws the *true* output length
and hides it in a `Truth` record that nothing downstream can see, because a real system does
not know how long a generation will run and every hard scheduling problem here follows from
that ignorance.

Issao: We should have an interface that defines the shape of load that the workload generator
will generate.

The request enters a **gateway**, which owns rate limiting and the outermost admission
decision. Rate limits are denominated in tokens, not requests, because a single
hundred-thousand-token prompt costs what twenty-five chat turns cost. The gateway consults an
admission policy and may shed immediately, which is the cheap failure, deliberately distinct
in the outcome enum from shedding after GPU time has been spent.


A **router** picks a replica. It sees only a delayed fleet snapshot, so this is where herding
lives: with many routers reading one stale snapshot, all of them conclude the same replica is
idle. The router records which candidates it considered and how many cached prefix tokens it
believed the winner held, so both herding and affinity misprediction are measurable rather
than inferred.

A **replica engine** receives the request and is itself a scheduler. Under continuous
batching it decides every step whether to admit from its own queue, and it can preempt. So
there are two scheduling layers, router and replica, and they can work against each other.
The replica tracks resident KV in tokens against a fixed budget, splits long prefills into
chunks so one arrival cannot insert a two-second stall into everyone else's token stream, and
evicts to a **KV tier pool** when the budget runs out. Tokens stream back, and the client
observes time-to-first-token and inter-token latency as separate quantities.

If the client's deadline passes first, it cancels and possibly retries under a budget. A
retry here is far more expensive than in a stateless service, because thirty seconds of GPU
work has usually already been spent.

### 10.2 The control loop above it

Each replica samples itself on a period and publishes a snapshot to a **telemetry
collector**. The collector assembles fleet snapshots in which every entry carries its own
sampling timestamp, so a snapshot is a set of differently-aged observations rather than a
consistent cut. Real fleets have no consistent cut, and pretending otherwise is what makes
simulated load balancing look better than reality.

Routing, autoscaling and failure-detection policies all read from that delayed view and
nothing else. Freshness is purchasable, through a probe that costs a modelled round trip, so
the price of knowing more is visible rather than free.

The autoscaler acts through a **capacity manager**, and this is where the loop's dominant
delay lives. Provisioning takes from thirty seconds to five minutes, because tens to hundreds
of gigabytes of weights must be read and loaded. A burst develops in tens of seconds. So the
sensor period, the propagation delay, and that actuator delay together form a sampled-data
feedback system whose instability is not an accident but a prediction. Driving offered load
with a sinusoid and sweeping its frequency yields gain and phase, and therefore loop gain and
phase margin, which is how oscillation onset becomes something you compute rather than
something you notice.

### 10.3 The engine beneath both

Nothing above touches state directly. Policies return **intents**, and every intent passes a
**referee** that enforces the invariants a policy must not be able to break: KV is never
overcommitted, step budgets never exceed the engine maximum, no effect lands earlier than its
actuation delay, no intent references state newer than the observation it came from, and work
is never created or destroyed. In strict mode a violation aborts the run, which is what the
policy arena uses so that a cheating policy cannot score. Cheating is unrepresentable rather
than merely forbidden, because the observation type contains no fresh state and the intent
type cannot express an illegal action.

A **cost model** turns batch state into elapsed time. Between composition changes the batch is
fixed, so step time follows a linear recurrence and the sum of the next N steps has a closed
form. Advancing a replica is therefore a handful of arithmetic operations whether the next
event is three steps away or thirty thousand, and the simulation's cost stops depending on how
many tokens are generated.

A **two-level event queue** orders the fleet: each replica holds its own next-event time and a
small global heap orders the replicas. The global structure stays cache-resident regardless of
how many requests are in flight, which is the difference between the plan working and not.

**Seeded RNG streams**, named and independent, feed everything stochastic. Changing the
arrival rate must not perturb prompt lengths, and enabling failure injection must not perturb
the workload, or an A/B comparison silently compares two different worlds.

**Metrics** aggregate online, into histograms and fixed-rate series, with full traces kept
only for a stratified sample. At target scale a simulated hour completes hundreds of millions
of requests, so this is a constraint rather than a preference.

### 10.4 The product on top

A **runner** executes scenario sweeps in batch and emits a self-contained static HTML report.
A **server** exposes the control interface over real gRPC to a **React dashboard**, which is
both the interactive playground and the showcase of preloaded scenarios with their narration.
Scrubbing reads the recorded event log and needs no re-simulation; changing a parameter that
alters physics rewinds to a snapshot and re-simulates, and the response says so explicitly so
the interface never implies a continuity that does not exist.

### 10.5 Crates

Rust workspace. Dependency direction is strictly downward; nothing below depends on
anything above it.

| Crate | Responsibility | May not |
|---|---|---|
| `sim-core` | event queue, clock, RNG streams, determinism fingerprint | know about LLMs |
| `sim-physics` | referee, resource models, cost model, memory tiers | know about policies |
| `sim-model` | replica engine and epochs, cluster, fleet, prefix tree | mutate state outside referee |
| `sim-workload` | arrivals, sessions, tenants, prefix structure, trace replay | see replica state |
| `sim-policy` | policy trait and implementations | touch simulation state |
| `sim-metrics` | histograms, series, trace sampling, report output | affect simulation |
| `sim-proto` | generated types from `proto/` | contain logic |
| `sim-run` | scenario runner CLI, static HTML report | — |
| `sim-server` | backend service for the dashboard | contain simulation logic |
| `web/` | Node + React dashboard | — |

The invariant worth enforcing in CI: `sim-policy` must not be able to reach mutable
simulation state. Express it in the type system, not in a review guideline.

## 12. Open risks

1. ~~**Event queue throughput.**~~ **Closed.** Measured at 54 ns/event for a 6,250-entry
   `std::collections::BinaryHeap`, giving 2x headroom against the budget and reaching the 20x
   stretch target on one core. The two-level design is confirmed necessary, since heap size
   dominates; the hand-rolled heap proposed as its mitigation turned out to be slower than the
   standard library and is dropped. Section 1.4.
2. **Cost model calibration.** Ordering of policies must be robust to cost-model error. The
   mitigation is a sensitivity test: perturb the utilization and overhead constants by
   +/-30% and confirm that policy rankings do not flip. If a conclusion is not robust to
   that, it is not a conclusion.
3. **Batch-1 fixed overhead.** The primer notes measured single-stream decode is 2-3x the
   roofline. `t_fix` is therefore load-bearing and is the first thing to calibrate.
4. **Prefix cache memory.** Needs a hard per-replica node cap or fleet memory grows to
   several GB. Section 1.5.
5. **Speculative decoding variance.** Sub-epoch sampling understates burst-level variance.
   Acceptable if documented; a problem if someone studies short-timescale jitter.
6. **Workload realism.** The simulator can only be as realistic as its arrival process and
   its prompt and output length distributions. This is the least glamorous and most
   important thing to calibrate against published data.
7. **Frontend scope.** The dashboard described in VISION section 6 is a substantial product
   in its own right. It should be scoped separately from the engine, against a frozen
   metrics and control interface, or it will expand without limit.
