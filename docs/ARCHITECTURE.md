### 1.4 The event queue: measured, and the mitigation was wrong

This was open risk 1, the one number that could invalidate the plan. It is now measured, in
Rust, release build with link-time optimisation, on this machine. See `bench/queue/`.

The workload mirrors the real one: pop the earliest event, do trivial work, push that actor's
next event 1 ms to 1 s later. Ordering is by `(time_ns, seq)` in every variant, so the
determinism requirement is not traded away for speed.

| Structure | Entries | ns/event | Verdict vs 100 ns budget |
|---|---|---|---|
| std `BinaryHeap`, pop+push | 6,250 | **54** | inside, ~2x headroom |
| std `BinaryHeap`, pop+push | 62,500 | **82** | inside |
| std `BinaryHeap`, pop+push | 200,000 | 124 | marginal |
| std `BinaryHeap`, pop+push | 1,700,000 | **441** | 4.4x over budget |
| 2-ary `replace_min`, hand-rolled | 6,250 | 66 | slower than std |
| 4-ary `replace_min`, hand-rolled | 6,250 | 70 | slower than std |
| 8-ary `replace_min`, hand-rolled | 6,250 | 75 | slower than std |
| 4-ary with position tracking | 6,250 | 73 | slower than std |

Two conclusions, one of which corrects an earlier claim in this document.

**Confirmed: the two-level design is necessary.** Heap size dominates everything else. Going
from 6,250 entries to 1.7 million costs 8x per operation, entirely in cache misses during the
sift. So per-request timers such as client timeouts, deadlines and retries must *not* enter the
global queue. Keep one entry per replica in the global structure and hold each replica's own
future events locally, and the hot structure stays cache-resident no matter how many requests
are in flight.

**Corrected: do not hand-roll the heap.** An earlier draft of this section predicted 1-2
microseconds for the large flat heap and proposed a 4-ary implicit heap as the mitigation. The
prediction was pessimistic by roughly 3x, and the proposed mitigation is *slower* than the
standard library at every size tested, including the variant that avoids position tracking
entirely. Rust's `BinaryHeap` uses a hole-based sift that beats a straightforward swap loop,
and higher arity made things worse rather than better here. Use `std::collections::BinaryHeap`
and spend the effort on keeping it small.

| 20x (stretch) | 18 M | 0.97 |

## 3. Analytic epoch advancement

This is the core mechanism, so it is worth stating precisely.

### 3.1 The decode recurrence has a closed form

Within an epoch the batch composition is fixed: `B` sequences are decoding, none finishes,
none is admitted. From the primer's cost model, per-GPU bytes read at step `k` are the
weights plus the resident KV, and the resident KV grows by exactly `B` tokens per step.

Let `G` be tensor-parallel degree, `bw` HBM bandwidth, `u` memory-bandwidth utilization,
`kv` bytes of KV per token, `W` total weight bytes, `S0` resident KV tokens at epoch start,
and `t_fix` fixed per-step overhead. Then

```
alpha = kv * B / (G * bw * u)                     # step-time growth per step
beta  = (W + kv * S0) / (G * bw * u) + t_fix      # duration of the first step
t_step(k) = beta + alpha * k
```

Summing an arithmetic series gives the duration of `n` steps in closed form:

```
T(n) = n * beta + alpha * n * (n - 1) / 2
```

### 3.2 Advancing an epoch is O(1)

The next composition change is at `n* = min(tokens_remaining_i)` over the batch, available
in O(1) from a small min-structure per replica. The epoch therefore ends at `t + T(n*)`,
computed with a handful of arithmetic operations regardless of whether `n*` is 3 or 30,000.

If an external event lands mid-epoch at offset `d` (an arrival, a preemption order, a
policy decision), invert the quadratic to find how many steps have elapsed:

```
n = floor( ( -(beta - alpha/2) + sqrt( (beta - alpha/2)^2 + 2*alpha*d ) ) / alpha )
```

Advance the epoch state to step `n`, apply the event, and open a new epoch. Also O(1).

### 3.3 What this buys, and what it costs

- Cost becomes O(composition changes), independent of token counts. This is exactly the
  principle you stated in VISION section 4: work scales with number of requests, not with
  the size of the work in each request.
- It is **exact**, not approximate, given the linear-bandwidth cost model. The
  approximation lives in the cost model, which is calibrated, not in the integration.
- Per-sequence identity, arrival order, and completion times are all preserved, so tail
  latency and per-tenant fairness remain measurable.

### 3.4 Where it needs care

**Prefill.** Chunked prefill has a real per-chunk structure, so a prefill costs
`ceil(prompt_tokens / chunk_budget)` epoch boundaries. For a 2k prompt at an 8k budget that
is one; for a 128k prompt it is sixteen. Small constant, and it is physical rather than an
artifact. Acceptable.

**Speculative decoding.** Tokens per step becomes a random variable, which breaks the
closed form. Three options: sample per step (back to per-token cost), use the expected
acceptance rate for a whole epoch (cheap, understates variance), or **sample once per
sub-epoch of N steps** (variance at a configurable timescale, cost multiplied by
steps/N). Recommend the third with N tunable, and document that burst-level variance below
the sub-epoch timescale is understated. Note also that acceptance rate falls as batch size
rises, so the acceptance model must be a function of batch state, not a constant.

**Policies that want to act every step.** This is the real cost driver, and it is the honest
fidelity dial:

| `decision_interval` | Epoch boundaries added | Cost multiplier |
|---|---|---|
| `on_change` (default) | none | 1x |
| `every_n_ms = 100` | ~10/s per replica | ~1.1x |
| `every_n_steps = 10` | ~4/s per replica | ~1.04x |
| `every_step` | ~40/s per replica | ~1.4x |

Even `every_step` is only about 1.4x, because 40 steps/s is small next to the ~100
composition changes/s. **So per-step policy decisions are affordable after all.** The thing
that is not affordable is per-step *iteration over every sequence*, which is a different
matter and is what the epoch form eliminates.

### 3.5 Validated numerically

`bench/validate_epochs.py` checks the claim rather than asserting it. Three properties, all
passing:

- **The closed form equals the step-by-step sum exactly**, checked in rational arithmetic
  rather than floating point, across batch sizes from 1 to 256 and up to 30,000 steps. A match
  in exact arithmetic is a proof for those inputs, not a coincidence of rounding.
- **The inverse solve is correct** on 20,000 randomised trials plus exact-boundary cases: for a
  mid-epoch event at offset `d`, the returned step count `n` satisfies `T(n) <= d < T(n+1)`.
- **A whole replica run agrees.** Sequences with different remaining lengths, completing at
  different times, produce identical completion times either way. Worst relative difference
  across cases was 1.7e-15, which is float noise and not algebraic disagreement. The same runs
  took 23,343 per-step iterations versus 285 epoch iterations, a factor of 82.

A side finding worth keeping: the closed form is *more* accurate than the loop, not merely
faster, because it does not accumulate rounding error over n additions. That removes the last
reason someone might prefer per-step iteration.

The same script reproduces the decode step-time table in `docs/llm-serving-primer.md` section
10.4 to within 0.1 ms at every row, which is a useful check that the algebra here and the
hand-computed numbers there describe the same model.

## 4. Request cohorts: parked, with a trigger and a knob

**Status: parked at Issao's direction.** The analysis below stands on its merits, and Issao
accepts it as an argument without accepting it as a closed decision. Recorded here as a
reserve option with an explicit trigger, so the choice can be revisited on evidence rather
than re-argued.

### 4.1 Why aggregation is expensive in fidelity

**The problem cohorts solve is not currently the bottleneck.** Cohorts reduce per-request cost.
At target scale that is ~165 MB of state and ~112,500 arrivals/s, and the measured event queue
runs at 54 ns/event with 2x headroom, section 1.4. The expensive thing was per-token work, and
analytic epochs remove that completely at no fidelity cost.

**Aggregation attacks the heterogeneity that causes the dynamics.** Every phenomenon in
`VISION.md` section 3a is driven by differences *between individual requests*:

- Rolling hotspots exist because request sizes differ. A cohort with a mean size has no hotspot
  to roll.
- Head-of-line blocking is one long request stalling many short ones. Averaged into a cohort,
  the stall disappears.
- Preemption cascades start when a few sequences outrun their expected output length. Cohort
  means cannot express "a few".
- Goodput, p99 and p99.9 are order statistics over individual requests, and cannot be recovered
  from cohort aggregates. The entire scorecard is per-request.

**The dial is not monotone in usefulness.** It is monotone in cost, but fidelity collapses
non-linearly: the first increment of aggregation removes the heterogeneity, which is where
nearly all the interesting behaviour lives.

### 4.2 The knob, if it is ever needed

Issao's framing is a single parameter spanning fully-discrete to fully-fluid. Concretely:

| `cohort_size` | Behaviour | Cost | Fidelity |
|---|---|---|---|
| 1 | every request individual | baseline | full |
| k | requests batched into groups of k sharing one size draw | ~1/k of per-request cost | tail statistics degrade sharply with k |
| infinity | one fluid flow per tenant per cluster | negligible | envelope only |

Two design rules keep it honest if built:

- **Cohorts must be homogeneous by construction**, grouping only requests already similar in
  prompt length, output length and SLO class. Grouping across a bimodal mixture is what destroys
  head-of-line blocking, so the grouping key must include the mode. This preserves *some* of the
  heterogeneity that matters, at the cost of needing many cohorts where the distribution is wide.
- **Any scorecard computed from cohorts must be labelled as such**, and percentile fields must be
  reported as absent rather than estimated. Estimating p99 from cohort means would be the single
  most dangerous thing this simulator could do.

### 4.3 Trigger to revisit

Build this only if one of these becomes true, and record which:

1. A single cluster at target scale cannot reach 2x realtime on one core. Currently it reaches
   20x with headroom, section 1.4, so this is not close.
2. Memory for in-flight requests exceeds the budget of a single machine. Currently ~165 MB at
   6,250 replicas, section 1.5.
3. A scenario requires simulating days of traffic where only the aggregate envelope matters, and
   the fully-fluid end of the knob is the cheapest way to fast-forward.

### 4.4 What ships instead, now

The narrow aggregate uses that are clearly worth having, all opt-in and labelled approximate:

1. **Background regions.** In a five-cluster geo scenario studying cluster 2, simulate the other
   four as fluid so they still create realistic cross-region routing pressure and shared-capacity
   contention, at ~1% of the cost.
2. **Warm-up.** Reach a realistic steady state quickly before switching to request-level.
3. **Long-horizon fast-forward.** Days of diurnal traffic for autoscaling drift, with
   request-level enabled only in windows of interest.

This is a `fidelity = full | fluid` flag *per cluster and per time window*, which is the
fully-fluid end of Issao's knob applied selectively rather than globally. It preserves full
fidelity where the experiment is looking, and is the recommended first step along that axis.

## 5. Engine, policy, and the physics referee

Your section 10 concern, resolved.

### 5.1 Policies produce intents, never mutations

A policy is a pure function from a **stale observation** to a list of **intents**. It holds
its own private state (estimators, EWMAs, controller integrators) but never touches
simulation state.

```
trait Policy {
    fn decide(&mut self, obs: &Observation, out: &mut IntentBuffer);
}
```

Intents are a closed enum: `Route`, `Admit`, `Reject`, `Enqueue`, `Preempt`, `Resume`,
`SetStepBudget`, `SetBatchLimit`, `MigrateKv`, `ScalePool`, `EjectReplica`, `Retry`.

### 5.2 The referee enforces physics

Every intent passes through a referee that checks the invariants a policy must not be able
to violate:

- **Conservation.** Tokens are neither created nor destroyed; a request's output length is
  fixed by the workload model, not choosable by the scheduler.
- **Capacity.** Resident KV tokens never exceed a replica's budget. Step token budget never
  exceeds the engine maximum. Batch size never exceeds `max_num_seqs`.
- **Causality.** No intent may reference state newer than the observation it was derived
  from, and no scheduled effect may land earlier than the applicable actuation delay.
- **Bandwidth.** Every KV migration debits the shared fabric or tier bandwidth for its
  duration.
- **Work completion.** Admitted work is either completed, preempted, or explicitly failed.
  It cannot silently vanish.

Two modes: `strict` aborts on violation, used in tests and in the policy arena so a cheating
policy cannot score; `tolerant` clamps and records a counter, so an agent-written policy
degrades instead of crashing a long run.

This is what makes the agent arena in your section 10 trustworthy. Cheating is not
punished after the fact, it is unrepresentable: the observation type has no fresh state in
it, and the intent type cannot express a physics violation that the referee will pass.

### 5.3 The performance worry does not materialize

You suspected the policy would need to compute machine state itself for speed. With
analytic epochs the engine's cost per decision is a handful of arithmetic operations, so
there is nothing to gain by moving that into the policy. Keep the separation clean.

## 6. Staleness, delay, and the control-theory angle

This deserves first-class treatment because it is your most distinctive goal, and it is
cheap to build.

### 6.1 Every observation is delayed by construction

```
replica true state
  -> sampling (period T_s, jitter)          # sensor
  -> publish (propagation delay, loss)      # transport
  -> consumer's last-known value            # zero-order hold
  -> Observation handed to policy           # the only thing a policy can see
```

The `Observation` type contains a timestamp and no channel to fresh state. A policy that
wants fresher information must pay for it in the model, for example by probing, which costs
a modelled RPC. That makes the cost of freshness visible rather than free.

### 6.2 The loop is a textbook sampled-data control system

- Plant: replica queues and KV occupancy.
- Sensor: telemetry with period `T_s` and delay `tau`.
- Controller: the load-balancing or autoscaling policy.
- Actuator: routing takes effect after an RPC delay; autoscaling after cold start, which is
  30-300 s from the primer. That is an enormous actuator delay and the reason reactive
  autoscaling oscillates.

Two features worth building because they turn this from an anecdote into analysis:

1. **Perturbation input.** Drive offered load with a step, or a sinusoid at frequency `f`,
   independent of the baseline workload.
2. **Frequency sweep.** Run the sinusoid across a range of `f` and record gain and phase
   from offered load to observed queue depth. That produces an empirical Bode plot, from
   which you get loop gain and phase margin, and you can *predict* the onset of oscillation
   rather than just observe it. Comparing a naive proportional controller against one with
   damping or a delay-compensating estimator then becomes quantitative.

I have not seen this done for inference serving. It is a genuinely novel and cheap addition,
and it makes the "value of robust control logic" claim measurable.

### 6.3 Gray failure

Replica health is a vector, not a boolean:

| Field | Meaning |
|---|---|
| `announced_state` | what the replica reports: healthy, draining, down |
| `speed_multiplier` | true throughput scaling; 0.1 is a thermal or degraded-link straggler |
| `accept_but_stall` | accepts requests and never completes them: partition or deadlock |
| `telemetry_state` | stale, frozen, or lying |

Silent slowdown is `announced_state = healthy` with `speed_multiplier = 0.1`. Detection
latency then becomes a measurable policy property rather than an assumption.

## 7. Data locality

### 7.1 KV capacity is the primary constraint

Per replica, KV capacity in tokens is
`(HBM_per_GPU * G - weight_bytes - workspace) / kv_bytes_per_token`, about 1.37 M tokens
for the reference config. Model it as a token counter with block-granularity rounding.
PagedAttention makes fragmentation a second-order effect, so it is out of scope.

The live KV and the prefix cache **compete for the same budget**. That coupling is a real
dynamic: under load the prefix cache is squeezed, hit rate falls, prefill work rises, and
load rises further. Model the split as a policy knob, because it is one in reality.

### 7.2 Memory tiers: pool them at cluster level

From the primer's locality table, for a 1.31 GB sequence of KV:

| Path | Bandwidth | Time |
|---|---|---|
| GPU to local host DRAM, PCIe5 | 64 GB/s | ~20 ms |
| GPU to remote host DRAM, 1 RDMA rail | 50 GB/s | ~26 ms |
| GPU to remote host DRAM, 8 rails | 400 GB/s | ~3.3 ms |
| GPU to local NVMe | 10 GB/s | ~131 ms |

**Local and remote DRAM are within ~20% of each other, and both are ~1000x slower than
HBM.** Issao's hypothesis holds, and he confirms the same treatment for SSD: **DRAM and SSD are
both fully disaggregated at the cluster level.** A replica reaching either tier pays a network
transfer regardless of which host physically holds the bytes, so per-host placement is not worth
modelling. Recommendation:

| Tier | Model as | Capacity | Bandwidth |
|---|---|---|---|
| 0: replica HBM | per replica | tokens | implicit in step cost |
| 1: cluster DRAM pool | per cluster | tokens | shared bytes/s |
| 2: cluster SSD pool | per cluster | tokens | shared bytes/s |
| 3: gone | — | — | recompute cost |

A sequence's KV carries a tier tag plus an owner id. Migrations are events that debit shared
bandwidth for their duration, so contention emerges naturally. Cost is O(1) per migration,
and migrations happen on preemption and resume, which are rare next to tokens.

Add per-host detail only to study capacity imbalance within a tier, which is not currently a
goal. Note the shared NIC bandwidth is also consumed by weight loading and any cross-node
parallelism, so tier 1 and 2 bandwidth must be genuinely shared resources.

Because the tiers are cluster-wide and the Leaf layer is sharded by machine (section 10), the
tiers are the one piece of simulated state that crosses a shard boundary. Section 10.6 resolves
that: a tier operation is a modelled network round trip to the tier owner, which is both
physically faithful and shard-safe.

### 7.3 Prefix caching: feasible, recommended

You suspected this approaches a cluster-wide virtual memory table. It does not, because of
one observation: **you never need to model content, only how much of a request's prompt is
already resident on a given replica.**

Represent shared prefixes as a **tree of segments**:

```
PrefixNode { parent: NodeId, tokens: u32, id: NodeId }
```

- A request carries one `NodeId` plus its own unshared suffix length.
- Sharing is *generated by the workload model*, not discovered from content. Turn N of a
  session extends turn N-1's node. A shared system prompt is a common root. A multi-agent
  fork or a tree search creates siblings under a shared parent. This is exactly the
  structure real traffic has, and it is free to construct.
- Per replica, a hash map from `NodeId` to residency, with an LRU over nodes.
- Hit length on replica R = walk from the request's node up through ancestors, summing the
  tokens of resident ones. Depth is a handful, so the lookup is O(depth), independent of
  prompt length.

Cost: O(1) to O(depth) per request. Memory: one entry per cached node per replica, which
must be capped, see section 1.5. Eviction competes with live KV, which is the coupling that
makes it interesting.

This directly supports the affinity questions in your section 3b, including the failover
cascade in 3a: when an affinity hotspot fails over, the new replica has a cold cache, its
prefill load spikes, and it becomes slow, which is the cascade. That dynamic is only
reachable if prefix state is modelled. **Recommend building it, in phase 2.**

### 7.4 Model weights and MoE

Lower priority per your VISION. The mechanism is the same tiering machinery: weights are
just another object with a size and a residency tier, and a cold replica pays a load cost.
Multi-model serving then becomes a cache-replacement problem over weights, which reuses
tier 1 and 2. MoE expert imbalance needs expert-parallel modeling to be meaningful and is
deferred. Design the tier machinery so weights can be added without touching it.

## 8. Determinism, replay, and observability

### 8.1 Determinism

One global seed. Named independent streams derived from it, so that changing the arrival
rate does not perturb prompt lengths, and enabling failure injection does not perturb the
workload. Without stream independence an A/B comparison silently compares two different
workloads. Stream names are hashed with a stable hash, never a per-process-salted one.

The engine's tie-breaking must be total and payload-independent: order by
`(time, priority, sequence_number)` where sequence number is a monotonic insertion counter.
No iteration over a hash map may ever influence scheduling order. A run should emit a
fingerprint, for example event count plus a rolling checksum of applied intents, so
determinism is a test rather than a hope.

### 8.2 Replay and the fast-forward/rewind UI

Two candidate mechanisms, and the cheap one is better:

- **Snapshot and re-simulate.** State is ~1.3 GB, so snapshots are expensive to take often.
  Use a coarse interval, for example every 60 simulated seconds, for long runs.
- **Observable event log, recommended for the UI.** Record what the dashboard can display:
  time series, histograms per interval, and sampled request traces. Scrubbing, fast-forward,
  and rewind then read the log with no re-simulation at all. Only a parameter change
  requires re-running.

So: log-driven scrubbing for the interactive dashboard, coarse snapshots only to bound
re-simulation cost when a user changes a parameter mid-run.

### 8.3 Metrics must aggregate online

An hour at target scale is ~405 M request completions. Design accordingly:

| Data | Mechanism | Volume |
|---|---|---|
| Latency distributions | HDR-style histograms per (cluster, tenant, SLO class, interval) | bounded |
| Time series | fixed-rate gauges, time-weighted | bounded |
| Counters | monotonic totals | trivial |
| Full request traces | reservoir sampling, uniform **plus** per-latency-bucket | bounded, tunable |

Your requirement for latency-bucket-stratified trace sampling is essential rather than
optional: uniform sampling of 405 M requests will contain almost no p99.9 examples, and
those are the ones worth reading. Stratify by outcome and latency bucket so the interesting
tail is always represented.

## 9. Parallelism

Superseded in part by section 10, which records Issao's three-layer deployment. This section
keeps the measurements and the reasoning that constrain it.

**Within one simulation, compute is not the reason to shard.** Section 1.4 measures one core
clearing 20x realtime for the whole 6,250-replica fleet. So sharding is driven by architectural
realism and headroom, not by necessity. That is worth knowing, because it means the sharding
design can be chosen for faithfulness and can afford synchronisation overhead.

**Across simulations, sharding is free and is the parallelism that pays.** The primary use is
A/B comparison, so running twenty scenario variants concurrently needs no time synchronisation
and is trivially deterministic. Ten backend replicas serve many concurrent runs; they do not
split one run. Anyone tempted to build a distributed time-warp engine for a single run should
read section 10.5 first.

**An earlier draft of this section recommended against intra-cluster parallelism.** That is
withdrawn. Issao's Leaf layer shards in the machine dimension, and section 10.5 shows the
sharding boundary he chose, whole nodes per shard, is exactly the boundary that makes
conservative synchronisation cheap. The warning that survives is narrower and concerns process
boundaries, not threads.

## 10. Deployment architecture and data flow

**Plan of record, supplied by Issao 2026-09-06.** His sketch is reproduced faithfully below and
then worked out, including the two open questions it raises: what state Ingress can afford, and
how Leaf sharding coexists with deterministic simulation.

### 10.1 Three layers

| Layer | Language | Sharding | Owns |
|---|---|---|---|
| **Frontend** | Node + React, browser | n/a | display only; no simulation state |
| **Ingress** | Rust | not sharded initially | all global and cluster-wide policies; per-replica control state; cluster memory tiers; metric merge; the Frontend API; run lifecycle |
| **Leaf** | Rust | machine dimension, **whole nodes per shard** | replica physics: continuous batching, epochs, KV accounting, preemption, prefix trees; per-shard statistics. The bulk of the work |

Two consequences of Issao's choice of sharding dimension, both good:

- **A replica is already a failure domain and its KV is local to it**, so splitting by whole
  nodes means no simulated state is shared between shards except the cluster memory tiers,
  handled in 10.6. There is no distributed KV cache to keep coherent.
- **It matches the real system.** In production, routing decisions are made centrally on stale
  summaries while replica scheduling happens locally on exact local state. The Ingress/Leaf split
  reproduces that asymmetry structurally, which means the staleness dynamics in section 6 are a
  property of the architecture rather than something bolted on.

### 10.2 Frontend to Ingress: the subscription contract

Issao's requirement, verbatim in spirit: this flow must be **O(1)**, meaning it must not scale
with the number of machines, the number of requests, or the ratio of simulated to real seconds.
Subscriptions must not change simulation behaviour, must be time-leased, must cover only what is
displayed, and machine views must be paginated.

**Commands** (all O(1) in payload): start a run, change parameters, rewind to a simulated time,
step forward a bounded amount, set a fixed simulation speed, open or renew or close a
subscription.

**How the O(1) guarantee is actually enforced.** A subscription that names a simulated sampling
interval is *not* sufficient, because raising the simulation speed then raises the wire rate
proportionally, which is the exact failure Issao named. So a subscription declares a
**wall-clock budget** and the server adapts to it:

| Field | Meaning |
|---|---|
| `max_updates_per_wall_second` | hard cap on emission rate |
| `max_rows_per_update` | hard cap on payload width |
| `desired_sim_interval_ns` | the client's preference, honoured only when it fits the budget |
| `lease_ns` | wall-clock lease; the server drops the subscription when it expires |

Ingress knows the current realtime factor, so it derives the effective simulated sampling
interval as `max(desired_sim_interval_ns, realtime_factor / max_updates_per_wall_second)` and
decimates further whenever the run speeds up. The client sets a budget it can consume; the
server never exceeds it. That makes the bound hold under a speed change rather than only at the
speed the client assumed.

**Pagination.** Any per-machine view names a sort key, a page size and a cursor. Ingress streams
that page only. Changing page replaces the subscription. Payload width is therefore bounded by
`max_rows_per_update` regardless of fleet size, which is what keeps a 62,500-replica run as
cheap to observe as a 100-replica one.

**Leases.** A closed browser tab must not leak a subscription that keeps Ingress and every Leaf
computing and shipping data forever. Leases expire; the Frontend renews what it still displays.

**Non-interference, and how it is guaranteed rather than promised.** Each Leaf maintains a fixed,
bounded set of aggregates for every simulated second, whether or not anything is subscribed. A
subscription selects which of those are *transmitted*, never which are *computed*. So no
subscription can perturb the run, and the determinism fingerprint in section 8.1 is identical
whether a dashboard is attached or not. Metrics that are genuinely expensive to maintain are
enabled at *scenario* level, where they become part of the run's identity, not at subscription
level.

**End of run.** Reported as a final subscription time point rather than a separate result
message, per Issao's preference for interface symmetry. A client that stays subscribed receives
the terminal values on the same channel it was already reading.

### 10.3 Ingress to Leaf, and back

**Ingress to Leaf: work dispatch.** Shaped like a real routing layer, one `Execute` per routed
request, so the modelled RPC latency and loss apply here and this hop *is* the router-to-replica
edge in the diagram. Ingress also opens metric subscriptions on each Leaf, using the same
mechanics as 10.2.

**Leaf to Ingress: two flows that must not be confused.** Issao's sketch mentions both; keeping
them separate is important because they have different scaling laws and only one of them is
allowed to be O(1).

| Flow | Purpose | Scales with | Cadence |
|---|---|---|---|
| **Control telemetry** | routing, autoscaling, ejection decisions | number of machines, necessarily | the scenario's telemetry publish interval |
| **Observability metrics** | dashboards, reports | nothing; O(1) per shard per subscription | the subscription's derived interval |

Control telemetry carries per-replica state: queue depth, resident and capacity KV tokens, HBM
cache status, health, recent latencies. It **must** scale with machine count, because a real
control plane does scrape every replica, and the cost and staleness of doing so is one of the
things being studied. Compressing it away would delete the phenomenon.

What it must *not* do is cost one message per replica. Each Leaf batches all of its replicas'
states into one message per publish interval, so message count is O(shards) while bytes stay
O(machines). At 6,250 replicas, eight shards and a 1 Hz publish interval: eight messages per
simulated second carrying roughly 1 MB in total, so about 20 MB/s of in-process traffic at 20x
realtime. Fine as threads; heavy but survivable as gRPC.

Observability metrics are aggregated **in the Leaf**, per Issao's instruction that the bulk of
the statistics work belongs there. Each Leaf ships fixed-size summaries: mergeable histograms,
counters, and its own time series. Ingress merges rather than computes. Histograms merge exactly
by bucket-wise addition, which is why the HDR-style representation in `metrics.proto` matters:
percentiles computed after merging are correct to bucket resolution, whereas percentiles cannot
be recovered from per-shard percentiles at all. Payload size per shard per subscription is
independent of how many replicas or requests that shard holds, which is the O(1) property.

Traces are sampled in the Leaf against a per-shard quota, so the total kept is bounded no matter
how many shards exist.

### 10.4 What state Ingress can afford

Issao's open question. **Memory is not the constraint. Per-decision compute is.**

Memory, at 6,250 replicas and 1.7 M requests in flight:

| State at Ingress | Size | Total |
|---|---|---|
| Per-replica control view | ~128 B | 0.8 MB (8 MB at 62,500 replicas) |
| Per-in-flight-request routing state | ~96 B | ~165 MB |
| Per-tenant aggregates for fair queueing | trivial | < 1 MB |
| Cluster tier accounting | trivial | < 1 MB |
| Prefix-affinity index | **must be capped** | see below |

Everything but the affinity index is comfortable. The affinity index is the one that can grow
without bound, because a naive map from prefix node to holding replicas grows with the number of
distinct cached prefixes fleet-wide. Cap it: Ingress holds a bounded top-K popular-prefix index
plus each replica's summary counters, and nothing else. Real routers work from exactly such a
summary, so the cap is faithful rather than a compromise. The full per-replica prefix tree stays
in the Leaf that owns the replica.

**The real constraint is that a routing decision must be O(1) or O(log N), never O(N).** At 20x
realtime Ingress makes 2.25 M routing decisions per second:

| Per-decision cost | CPU per wall second at 20x | Verdict |
|---|---|---|
| 100 ns, e.g. power-of-two-choices | 0.22 core | fine, unsharded |
| 1 us | 2.25 cores | Ingress must shard |
| O(N) scan of 6,250 replicas, ~6.25 us | 14 cores | impossible |

So **a full fleet scan per request is banned at scale**, and this is a constraint on policy
implementations rather than on the engine. "Least loaded" must be an incrementally maintained
index, not a scan. Sampling policies such as power-of-two-choices are naturally O(1), which is a
second independent reason to prefer them beyond their robustness to stale data, section 6.

This should be measured, not assumed: the harness should record per-decision CPU cost for each
policy and fail a run whose routing cost would not hold at target scale. A policy that only
works at small fleet sizes is worse than no policy, because it will produce a conclusion that
does not transfer.

Issao's "not sharded initially" is therefore correct, and stays correct as long as this
constraint is enforced.

### 10.5 Leaf sharding and determinism

This is the hard part, and the numbers decide it.

Deterministic parallel discrete-event simulation needs conservative synchronisation: a shard may
advance only as far as it can prove no message will arrive. The proof comes from **lookahead**,
the minimum latency of any message that could reach it. Here that is the Ingress-to-Leaf work
dispatch latency, which is the modelled router-to-replica RPC: **0.2 to 1 ms**.

Barriers per wall-clock second are `realtime_factor / lookahead`. At 20x realtime with a 0.5 ms
lookahead that is **40,000 barriers per second**.

| Shard boundary | Cost per barrier | CPU per wall second | Verdict |
|---|---|---|---|
| Threads, shared memory, atomics | 1-5 us | 0.04-0.2 s | comfortable |
| Processes, gRPC on localhost | 50-100 us | 2-4 s | breaks the target |

**Recommendation: Leaf shards are threads within one process per simulation run.** The Leaf
interface is still defined in proto and the boundary is still real, so the shards can become
processes later, at a reduced realtime factor or with a larger lookahead. Cross-process
parallelism is used *between* independent runs, where it costs nothing.

The escape hatch, if cross-process Leaf ever becomes necessary: raise the effective lookahead by
dispatching work in windows larger than the true RPC latency. That is a genuine fidelity
compromise, because requests would then arrive in batches rather than continuously, so it must
be opt-in, named in the scenario, and reported in the run record. It is not a free win.

Determinism across shards requires one more thing beyond the barrier: **a total order on
messages arriving at the same simulated time from different shards.** Order by
`(time_ns, shard_id, sequence_within_shard)`. Never by arrival order at the receiver, which
depends on thread scheduling and would make runs irreproducible. This is the single easiest
place to accidentally lose determinism, and it deserves a dedicated test that runs the same
scenario at several shard counts and asserts identical fingerprints.

### 10.6 Cluster-wide state that crosses shards

The cluster DRAM and SSD tiers, section 7.2, are the only simulated state shared across
machine-dimension shards. A Leaf preempting a sequence needs to know whether the tier has
capacity and what the transfer will cost, and that depends on contention from other shards.

Resolution: **the tier is owned by Ingress, and a tier operation is a modelled network round
trip to it.** This is physically faithful rather than a workaround, because moving KV to a
cluster-pooled tier genuinely is a network operation, so paying an RPC for it is what a real
system does. It also keeps every shard free of shared mutable state.

Volume is not a concern: tier operations happen on preemption and resume, which are rare
relative to tokens, and each is a small message.

### 10.7 Rewind, step, and speed

All three live at Ingress, which drives the Leaf shards' window advance.

- **Set speed.** A fixed realtime factor, or unbounded. Ingress paces the barrier loop, and the
  derived metric sampling interval in 10.2 follows automatically.
- **Step forward.** Advance a bounded number of simulated nanoseconds or barrier windows, then
  pause. Bounded so the Frontend request stays O(1) regardless of how much simulated time it asks
  for.
- **Rewind.** Cheap when only the view changed: read the recorded observability log, section 8.2,
  with no re-simulation. Expensive when a parameter that alters physics changed: restore the last
  snapshot and re-simulate, which is why snapshot interval is a tunable. The response must state
  which of the two happened, so the interface never implies a continuity that does not exist.

### 10.8 Deployables and crates

Rust workspace. Dependency direction is strictly downward; nothing below depends on anything
above it. Three deployables map onto it.

| Crate | Deployable | Responsibility | May not |
|---|---|---|---|
| `sim-core` | both | event queue, clock, RNG streams, determinism fingerprint | know about LLMs |
| `sim-physics` | Leaf | referee, resource models, cost model | know about policies |
| `sim-model` | Leaf | replica engine and epochs, prefix tree | mutate state outside the referee |
| `sim-workload` | Ingress | arrivals, sessions, tenants, trace replay | see replica state |
| `sim-policy` | Ingress (global), Leaf (replica-local) | policy trait and implementations | touch simulation state |
| `sim-metrics` | both | histograms, series, trace sampling, merge | affect simulation |
| `sim-proto` | both | generated types from `proto/` | contain logic |
| `sim-leaf` | **Leaf** | shard runtime: owns replicas, serves the Leaf API | contain global policy |
| `sim-ingress` | **Ingress** | run lifecycle, global policy, tier ownership, metric merge, Frontend API | contain replica physics |
| `sim-run` | CLI | batch scenario sweeps, static HTML report | — |
| `web/` | **Frontend** | React dashboard | hold simulation state |

Two invariants worth enforcing in CI rather than in review:

- `sim-policy` must not be able to reach mutable simulation state. Express it in the type system.
- `sim-ingress` must not depend on `sim-model` or `sim-physics`. If it can compute replica
  physics, someone eventually will, and the layer boundary Issao specified will erode.

## 11. The system in words

`docs/diagrams/system.drawio` draws this, in two pages: the data plane with its policy
boundary, and the control plane with the engine and product surface. Every arrow there names
a `service.Method` in `proto/`, and `tools/check_diagram.py` fails if the diagram and the
interfaces disagree. What follows is the same thing in prose, which is the authoritative
version.

### 11.1 The life of a request

A **workload generator** stands in for clients. It draws an arrival time, a tenant, an SLO
class, a prompt length, and a shared-prefix identity. It also draws the *true* output length
and hides it in a `Truth` record that nothing downstream can see, because a real system does
not know how long a generation will run and every hard scheduling problem here follows from
that ignorance.

The request enters a **gateway**, which owns rate limiting and the outermost admission
decision. Rate limits are denominated in tokens, not requests, because a single
hundred-thousand-token prompt costs what twenty-five chat turns cost. The gateway consults an
admission policy and may shed immediately, which is the cheap failure, deliberately distinct
in the outcome enum from shedding after GPU time has been spent.

A **router** picks a replica. It sees only a delayed fleet snapshot, so this is where herding
lives: with many routers reading one stale snapshot, all of them conclude the same replica is
idle. The router records which candidates it considered and how many cached prefix tokens it
believed the winner held, so both herding and affinity misprediction are measurable rather
than inferred.

A **replica engine** receives the request and is itself a scheduler. Under continuous
batching it decides every step whether to admit from its own queue, and it can preempt. So
there are two scheduling layers, router and replica, and they can work against each other.
The replica tracks resident KV in tokens against a fixed budget, splits long prefills into
chunks so one arrival cannot insert a two-second stall into everyone else's token stream, and
evicts to a **KV tier pool** when the budget runs out. Tokens stream back, and the client
observes time-to-first-token and inter-token latency as separate quantities.

If the client's deadline passes first, it cancels and possibly retries under a budget. A
retry here is far more expensive than in a stateless service, because thirty seconds of GPU
work has usually already been spent.

### 11.2 The control loop above it

Each replica samples itself on a period and publishes a snapshot to a **telemetry
collector**. The collector assembles fleet snapshots in which every entry carries its own
sampling timestamp, so a snapshot is a set of differently-aged observations rather than a
consistent cut. Real fleets have no consistent cut, and pretending otherwise is what makes
simulated load balancing look better than reality.

Routing, autoscaling and failure-detection policies all read from that delayed view and
nothing else. Freshness is purchasable, through a probe that costs a modelled round trip, so
the price of knowing more is visible rather than free.

The autoscaler acts through a **capacity manager**, and this is where the loop's dominant
delay lives. Provisioning takes from thirty seconds to five minutes, because tens to hundreds
of gigabytes of weights must be read and loaded. A burst develops in tens of seconds. So the
sensor period, the propagation delay, and that actuator delay together form a sampled-data
feedback system whose instability is not an accident but a prediction. Driving offered load
with a sinusoid and sweeping its frequency yields gain and phase, and therefore loop gain and
phase margin, which is how oscillation onset becomes something you compute rather than
something you notice.

### 11.3 The engine beneath both

Nothing above touches state directly. Policies return **intents**, and every intent passes a
**referee** that enforces the invariants a policy must not be able to break: KV is never
overcommitted, step budgets never exceed the engine maximum, no effect lands earlier than its
actuation delay, no intent references state newer than the observation it came from, and work
is never created or destroyed. In strict mode a violation aborts the run, which is what the
policy arena uses so that a cheating policy cannot score. Cheating is unrepresentable rather
than merely forbidden, because the observation type contains no fresh state and the intent
type cannot express an illegal action.

A **cost model** turns batch state into elapsed time. Between composition changes the batch is
fixed, so step time follows a linear recurrence and the sum of the next N steps has a closed
form. Advancing a replica is therefore a handful of arithmetic operations whether the next
event is three steps away or thirty thousand, and the simulation's cost stops depending on how
many tokens are generated.

A **two-level event queue** orders the fleet: each replica holds its own next-event time and a
small global heap orders the replicas. The global structure stays cache-resident regardless of
how many requests are in flight, which is the difference between the plan working and not.

**Seeded RNG streams**, named and independent, feed everything stochastic. Changing the
arrival rate must not perturb prompt lengths, and enabling failure injection must not perturb
the workload, or an A/B comparison silently compares two different worlds.

**Metrics** aggregate online, into histograms and fixed-rate series, with full traces kept
only for a stratified sample. At target scale a simulated hour completes hundreds of millions
of requests, so this is a constraint rather than a preference.

### 11.4 The product on top

A **runner** executes scenario sweeps in batch and emits a self-contained static HTML report.
A **server** exposes the control interface over real gRPC to a **React dashboard**, which is
both the interactive playground and the showcase of preloaded scenarios with their narration.
Scrubbing reads the recorded event log and needs no re-simulation; changing a parameter that
alters physics rewinds to a snapshot and re-simulates, and the response says so explicitly so
the interface never implies a continuity that does not exist.

### 11.5 Crates and layers

See section 10.8.

## 13. Open risks

1. ~~**Event queue throughput.**~~ **Closed.** Measured at 54 ns/event for a 6,250-entry
   `std::collections::BinaryHeap`, giving 2x headroom against the budget and reaching the 20x
   stretch target on one core. The two-level design is confirmed necessary, since heap size
   dominates; the hand-rolled heap proposed as its mitigation turned out to be slower than the
   standard library and is dropped. Section 1.4.
2. **Cost model calibration.** Ordering of policies must be robust to cost-model error. The
   mitigation is a sensitivity test: perturb the utilization and overhead constants by
   +/-30% and confirm that policy rankings do not flip. If a conclusion is not robust to
   that, it is not a conclusion.
3. **Batch-1 fixed overhead.** The primer notes measured single-stream decode is 2-3x the
   roofline. `t_fix` is therefore load-bearing and is the first thing to calibrate.
4. **Prefix cache memory.** Needs a hard per-replica node cap or fleet memory grows to
   several GB. Section 1.5.
5. **Speculative decoding variance.** Sub-epoch sampling understates burst-level variance.
   Acceptable if documented; a problem if someone studies short-timescale jitter.
6. **Workload realism.** The simulator can only be as realistic as its arrival process and
   its prompt and output length distributions. This is the least glamorous and most
   important thing to calibrate against published data.
7. **Frontend scope.** The dashboard described in VISION section 6 is a substantial product
   in its own right. It should be scoped separately from the engine, against a frozen
   metrics and control interface, or it will expand without limit.
