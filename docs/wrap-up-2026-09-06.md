Written 2026-09-06 21:02 PDT for Issao's review tomorrow. Every claim links to the thing itself. The

## 0. The one-paragraph version

In one day the project went from a vision document to a deterministic Rust simulator of an LLM inference
fleet that reproduces **nine named dynamics** with numbers, a dashboard that shows those dynamics three
ways (recorded, live, and stepped through as a walkthrough), an arena that scores policies and can write
new ones, and a public deployment that scales to zero. **11 of 11 selected dynamics have a showcase
walkthrough, 10 run live on the dashboard, and 10 open as a live run from the showcase**; the last step
(walkthrough `set` steps applying to a live run) landed at 20:59 (U59b). Two agent-architecture restarts
took the fleet from 8 merged units an hour to 32.

## 2. The nine findings

Full text with tables and the exact scenarios: [`docs/findings.md`](https://github.com/issao/lbsim/blob/master/docs/findings.md).
Each is reproducible with `./run-demos.sh`; every number is held by
[`bench/golden-fingerprints.txt`](https://github.com/issao/lbsim/blob/master/bench/golden-fingerprints.txt).

| # | Finding | The number | Report | Showcase |
|---|---|---|---|---|
| 1 | **Reading the whole fleet routes worse than sampling two of it.** Least-requests inspects all 32 replicas on a snapshot up to 1.2 s old and herds; power-of-two-choices does not | least-requests **2.6× worse** p99 than P2C, and worse than round robin | [1-routing](https://lbsim.ai/reports/1-routing.html) | `#/showcase` → routing |
| 2 | **Herding is a smooth, steep function of staleness.** Only the telemetry age changed | **12× goodput collapse** across scrape intervals that all look reasonable (100 ms → 4 s) | [2-staleness](https://lbsim.ai/reports/2-staleness.html) | staleness |
| 3 | **Prefill and decode contend for one device; no chunk size wins both.** TTFT and inter-token latency move in opposite directions monotonically | 18× range of worst inter-token gap across the sweep | [3-chunking](https://lbsim.ai/reports/3-chunking.html) | chunking |
| 4 | **Past the knee, more offered load delivers less work.** Two knees, in different places | goodput peaks at **150 rps (64% of rated 235)**, throughput at 190 | [4-load-curve](https://lbsim.ai/reports/4-load-curve.html) | load curve |
| 5 | **Capacity is a token budget; a load-balancer metric improves while service collapses.** Long-context share swept | load-spread CV **0.38 → 0.24 while goodput halves and tail latency gets 34× worse** | [5-long-context](https://lbsim.ai/reports/5-long-context.html) | long context |
| 6 | **A retry budget is the difference between a bad minute and an outage.** Same 3× spike, three retry policies; the unbudgeted one never recovers | metastable collapse vs full recovery | [6-retry](https://lbsim.ai/reports/6-retry.html) | retry |
| 7 | **The routing ordering does not need the decode physics.** Your `disable_decode` ("HBM to infinity") | P2C 97.0% vs round robin 93.7% attainment, ttft99 3.8 s vs 7.2 s at identical throughput | [7-no-decode](https://lbsim.ai/reports/7-no-decode.html) | no decode |
| 8 | **The KV spiral.** Parked multi-turn session context fills the cache; without eviction one sequence runs at a time; swapping to DRAM cures it | late attainment **2% → 95%**, p99 TTFT 36 s → 84 ms, goodput 780 → 1,426 tok/s | 11-preemption (next deploy) | preemption |

| 9 | **Speculative decoding pays at small batch and costs at large.** Scenario keys `spec_draft_tokens` / `spec_accept_rate`, off by default; the gain is the expected accepted tokens per step, the cost is the draft compute at large batch | see `docs/findings.md` §9 (U26; demo 12 wiring in flight) | (next deploy) | — |

Three more demos exist as reports and recordings without a numbered finding yet: [8-admission](https://lbsim.ai/reports/8-admission.html)
(deadline-aware admission at 1.4× rated: goodput 241 → 496 tok/s), [9-fair-share](https://lbsim.ai/reports/9-fair-share.html)
(weighted fair share over tenants: goodput 9,157 → 14,496, the over-share tenant is 100% of what is shed), and
[10-probes](https://lbsim.ai/reports/10-probes.html) (least-KV on live probes vs P2C under 4 s staleness: imbalance CV 0.44 vs 0.63).

What the first eight have in common, in the findings doc's words: every one is a *control* result, not a
capacity result. The fleet was below rated capacity in all of them; what failed was the information the
decision was made on.

## 5b. Known issue at close of day (2026-09-06 22:16 PDT), first in tomorrow's queue

**The live server on Cloud Run degrades after a handful of runs.** Verified in a browser after the
final deploy (revision `lbsim-00013-mvq`, master c22ea56, session affinity on):

- Alone, the live path works: the dashboard opens a run and advances at 1×; the first two or three
  showcase cards drive a live run with samples arriving. The same build passes the whole 50-check
  browser gate locally (`tools/qa/qa.js`, 15 walkthroughs, all live).
- After several runs on the public instance, `POST /v1/ingress/StartRun` hangs for the client's full
  timeout with no response, `OpenSubscription` returns no bytes, while `GET /health` and `GetRun`
  answer in 120 ms and the run threads keep advancing. Locally the same sequence streams 24 updates
  in 6 s. So it is an interaction with Cloud Run (proxy-held dead connections, request-scoped CPU,
  or a lock held across a write that never fails behind the proxy), not the engine.
- Ruled out tonight: the metric-rejection bug (fixed, 7d174d0), the pause race (fixed), instance
  affinity (enabled, c22ea56), the 64-connection cap (it answers 503 "busy", it does not hang),
  HTTP/2 vs 1.1, gzip, the cookie.
- Not yet fixed: U77 (idle-stopped runs must not count toward the eight-run cap; evict then reap) and
  the diagnosis above, recorded for the tech lead as the first unit tomorrow: reproduce with
  `QA_BASE=https://lbsim.ai node tools/qa/qa.js`, add a request log the server writes itself (the
  deploy account cannot read Cloud Logging, `docs/deploy.md`), and check every lock held across a
  socket write or a checkpoint write in `crates/sim-ingress/src/server.rs` and `run.rs` (U54, U56).
- Practical effect for the morning: the instance scales to zero overnight and comes back fresh; one
  viewer at a time should get a working live dashboard and showcase; a second browser tab or an
  abandoned one is what tips it over. The replay mode (`?server=off`) is unaffected.
